# Accessibility audit (`locum a11y-audit`)

`locum a11y-audit` reads a window's accessibility tree, the same tree screen
readers and locum selectors use, and reports controls that assistive
technology users cannot identify, reach or hit. By default it is
**read-only**: it never clicks, types, moves the mouse or focuses anything,
so it is safe to run against a live application. The opt-in
[`--tab-walk`](#keyboard-walk---tab-walk) mode is the one exception: it
presses Tab in one named window to check the keyboard focus order.

```text
$ locum a11y-audit Paint
window 'Untitled - Paint':
  error   unnamed-control   togglebutton (1589,227 50x50)
          togglebutton has no accessible name: a screen reader announces only "togglebutton"  ->  window "Untitled - Paint" group "Layers" togglebutton
1 finding (1 error, 0 warnings, 0 info) in 175 nodes of 1 window, 5.1s
```

That is a real finding: the unnamed **Layers** toggle button in Windows 11 Paint.

## Usage

```text
locum a11y-audit [WINDOW] [--json] [--max-depth N] [--min-target-size PX]
                 [--fail-on {error,warning,never}] [--time-budget SECONDS] [--no-selectors]
                 [--window TITLE --tab-walk [--max-tabs N] [--reverse] [--policy PRESET]]
```

| option | default | meaning |
|---|---|---|
| `WINDOW` | every window | title query: exact, case-insensitive substring or glob, the same matching as `locum tree --window` |
| `--json` | off | machine-readable report (see below) |
| `--max-depth N` | 32 | how deep to walk below each window |
| `--min-target-size PX` | 24 | minimum click-target size for `small-target`; `0` turns the rule off |
| `--fail-on` | `error` | exit with status 1 when there are findings at this severity or worse; `never` always exits 0 |
| `--time-budget SECONDS` | 30 | stop walking after this long and mark the report `truncated`; `0` means no limit |
| `--no-selectors` | off | skip building a selector for each finding (faster on huge desktops) |
| `--window TITLE` | | the window to audit, same as `WINDOW`; required by `--tab-walk` |
| `--tab-walk` | off | **sends keys**: also walk the focus order with Tab (see [below](#keyboard-walk---tab-walk)) |
| `--max-tabs N` | 200 | maximum Tab presses of the walk |
| `--reverse` | off | after a complete cycle, press Shift+Tab once per stop to check the reverse order |
| `--policy PRESET` | none | judge every key press against a safety policy preset (`strict`, `default`, `permissive`) |

Exit codes follow the rest of the CLI: `0` means no findings at or above
`--fail-on`, `1` means there are some (or the window was not found), `2` is a
usage error and `3` means no accessibility backend is available. You can use
it as a CI gate, for example against an app started in a test VM:

```sh
locum a11y-audit "Invoice Entry" --fail-on warning --json > a11y.json
```

From Python:

```python
from locum import Desktop
from locum.a11y import audit

report = audit(Desktop(), "Paint", max_depth=32, time_budget=30, min_target_size=24)
for f in report.findings:
    print(f.severity, f.rule, f.element, f.selector)
report.failed("error")      # -> bool
report.to_dict()           # the --json document
```

`audit()` also accepts a `Window`, an `Element` or an accessibility node, and
takes `rules=[...]` to run only some rules and `selectors=False`.

## Rules

Each finding has a rule id, a severity (`error`, `warning`, `info`), a
one-line element description (`describe_node`: role, name, id, bounds,
states), a selector that finds the element again, and its bounds. The rules
are deliberately conservative: a rule that cannot tell a defect from a
legitimate design stays silent or uses a lower severity.

Only visible elements are judged. Hidden or offscreen subtrees are walked but
not reported, apart from `offscreen-visible`.

### `unnamed-control` (error)

An interactive control has no accessible name, so a screen reader announces
only its role ("button"). The interactive roles are button, toggle button,
checkbox, radio button, link, menu item, tab, slider and split button, plus
list and tree items that are actionable (they expose invoke, select, toggle
or expand, or are selectable). An image that can be invoked counts as a
button.

The severity drops to **warning** when a child text or image is named, for
example a button that contains a "Print" label. Some screen readers read that
child, but the control itself should carry the name.

### `unlabeled-input` (error)

An edit, combo box or spin button has no accessible name or label. When a
text element just before it among its siblings looks like a visual label
("Email:"), the message says so: the label exists on screen but is not
associated with the field (UIA `LabeledBy`, `aria-labelledby`, AX title UI
element).

### `unnamed-image` (info)

An image has no name. This is fine for purely decorative images, so it is
only informational. Images inside a control, such as the icon of a toolbar
button, are never reported because the control provides the name.

### `unnamed-window` (warning)

A top-level window or dialog has no title, so users cannot tell it apart in
the task switcher or in a screen reader's window list.

### `not-focusable` (warning)

An enabled button, toggle button, checkbox, radio button, link, edit, combo
box, slider or spin button reports that it cannot receive keyboard focus, so
keyboard-only users cannot reach it.

This rule only runs when the backend reports focusability at all, meaning at
least one node in the window is `focusable` or `focused`. Backends that never
set the state would otherwise flag every control. UI Automation reports
`IsKeyboardFocusable`. Two cases are excluded because they are legitimately
unfocusable:

* Children of composite widgets that move focus with the arrow keys (toolbar,
  menu bar, menu, tab list, list, tree, table or grid, radio group, status
  bar, title bar, ribbon). These widgets use roving focus: the container takes
  focus, not each child.
* Window caption buttons (Minimize, Maximize, Restore, Close, Help) and
  anything inside a title bar. These are reached through the system menu
  (Alt+Space).

### `small-target` (warning)

An enabled button-like control (button, toggle button, checkbox, radio
button, combo box, spin button, slider, tab or split button) is smaller than
`--min-target-size` px, 24 by default, in either dimension. It is reported
only if the target also fails the **spacing exception** of
[WCAG 2.2 SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html):
a 24 px circle centred on the target must not touch another target or
another undersized target's circle. A small but isolated button passes.

Limitations, all of which keep the rule quiet rather than noisy:

* Sizes are physical pixels, as backends report them. At 150 % display
  scaling, 24 CSS px are 36 physical px, so the rule under-reports on
  high-DPI screens. Pass a scaled `--min-target-size` to be strict.
* Links are excluded because inline links in text are exempt in WCAG.
* A target whose small edge lies on an ancestor's edge is treated as clipped,
  for example a gallery row scrolled half out of view, and is not reported.
  The visible part is small, but the real control is not.
* Nested targets, such as a split button's arrow inside the button, are not
  treated as neighbours.

### `duplicate-name` (warning)

Two or more sibling controls with the same role share a name, so a screen
reader user hears "Delete, button" twice and cannot tell which row it
belongs to. This rule applies to buttons, toggle buttons, checkboxes, radio
buttons, links, tabs, edits, combo boxes, sliders and split buttons. List,
tree and menu items, rows and cells are excluded because repeated data
values (two files called `a.txt`) are not a defect. The first element of a
group is not reported; each later duplicate is.

### `offscreen-visible` (info)

The backend reports an enabled control as offscreen even though its bounds
lie entirely inside its visible parent and its window. Assistive tools that
trust the offscreen flag may skip such a control. Controls that were
scrolled out of view usually lie outside their parent, so they are not
reported.

## JSON output

`--json` prints `AuditReport.to_dict()`, plus `fail_on` and `failed`:

```json
{
  "windows": ["Untitled - Paint"],
  "nodes": 175, "elapsed": 5.1, "truncated": false, "min_target_size": 24,
  "counts": {"error": 1, "warning": 0, "info": 0},
  "findings": [{
    "rule": "unnamed-control", "severity": "error",
    "message": "togglebutton has no accessible name: ...",
    "element": "togglebutton (1589,227 50x50)",
    "selector": "window \"Untitled - Paint\" group \"Layers\" togglebutton",
    "bounds": {"left": 1589, "top": 227, "width": 50, "height": 50},
    "role": "togglebutton", "name": "", "window": "Untitled - Paint"
  }],
  "notes": [],
  "fail_on": "error", "failed": true
}
```

`notes` explains anything partial, such as a time budget that ran out, a
skipped `not-focusable` rule, or findings left without a selector.

## Performance

The audit reads each node's properties and children once into an in-memory
snapshot. Rules and selector generation then work on that snapshot instead of
making a cross-process accessibility call per property. Walking Paint (175
nodes) takes about 0.5 s. Most of the remaining time is the first selector:
proving that the window's selector prefix is unique walks every other window
once (about 2 to 5 s on a desktop with about 4,000 accessible elements).
After that, the proof is cached for the rest of the audit. Use
`--no-selectors` when you only need the findings.

## Keyboard walk (`--tab-walk`)

The static `not-focusable` rule can only see what the backend reports. The
keyboard walk checks what the keyboard actually does: it presses Tab
repeatedly, records the element that has the focus after each press, and
reports focus traps, focus that leaves the window, focus stops a user cannot
see or a screen reader cannot name, a tab order that jumps backwards, and
focusable controls Tab never reaches.

```text
$ locum a11y-audit --window "Invoice Entry" --tab-walk --reverse
window 'Invoice Entry':
  warning tab-unreachable   button "Attach" (420,380 80x30)
          button is focusable but Tab never reaches it: keyboard-only users cannot get to it  ->  window "Invoice Entry" button "Attach"
tab order of 'Invoice Entry' (5 stops, 6 Tab presses, cycle complete):
    1. edit "Customer" (20,40 240x28) [focused]
    ...
```

**It sends keyboard input**, so it is never on by default and has guard rails:

* **One named window only.** `--tab-walk` needs `--window TITLE` (or the
  positional `WINDOW`); it never presses anything into whatever window
  happens to have the focus. The window is activated first and must then be
  in the foreground, or the command stops before the first press.
* **Bound to that window.** Every press goes through the same input target
  binding as `locum type --window` (strict): when another window takes the
  focus, for example because you clicked somewhere, the next Tab is not sent
  and the walk stops with a note (`stopped: interrupted`).
* **Under the desktop input lock.** The whole walk holds the session-wide
  input lock, so another locum worker cannot interleave its own input.
* **Tab only.** Nothing but Tab is pressed, plus Shift+Tab with `--reverse`.
  No text, Enter, Space, Escape or clicks.
* **Focus is restored.** The element focused before the walk is focused again
  afterwards through the accessibility API (no key press, no click). If that
  fails, a note says so.
* **Safety policy.** `--policy PRESET` (CLI) or `policy=` / a
  `GuardedDesktop` (Python) judges every press like any other automated
  input: a refused press stops the walk (`stopped: refused`), and a dry-run
  policy sends nothing (`stopped: dry-run`).

Even so, a Tab is a real key press. A multi-line editor that accepts Tab as
text gets a Tab character inserted. The walk notices this (the field's text
changes), reports `tab-trap` and stops at once, but it does not undo the
inserted character. Run the walk against a test instance of the
application, not a window you are working in.

The walk ends when the focus returns to the first stop (a complete cycle),
after `--max-tabs` presses (default 200), or at the first trap, escape or
lost focus.

### Keyboard walk rules

| rule | severity | meaning |
|---|---|---|
| `tab-trap` | error | Tab leaves the focus where it was (a control that swallows Tab, or a field that takes it as text), or the focus loops among a subset of the stops and never returns to the first one |
| `tab-escape` | error | the focus left the window: another window is in the foreground, or the focused element is outside the window's tree |
| `tab-focus-lost` | warning | no element has the keyboard focus after a press |
| `tab-focus-invisible` | warning | the focused element is offscreen, invisible, has no bounds or lies entirely outside its window |
| `tab-focus-unnamed` | warning | the focused element has no accessible name |
| `tab-order-backwards` | info | the next stop lies before the previous one in reading order: above it and not to its right, or to its left on the same row. One wrap-around per cycle, the step to the stop that comes first in reading order, is expected and not reported. This is a heuristic: multi-column layouts can trigger it legitimately |
| `tab-unreachable` | warning | only after a complete cycle: an enabled, visible, focusable control (the `not-focusable` roles) that Tab never reached. Roving-focus children and caption buttons are excluded, as for `not-focusable` |
| `tab-order-asymmetric` | warning | only with `--reverse`: Shift+Tab from the first stop does not visit the stops in exactly the reverse order |

### From Python

```python
from locum import Desktop
from locum.a11y import audit, tab_walk
from locum.llm.safety import Policy

report = audit(Desktop(), "Invoice Entry", tab_walk=True, max_tabs=100, reverse_check=True)
for stop in report.tab_walk.stops:
    print(stop.index, stop.role, stop.name, stop.bounds, stop.selector)

walk = tab_walk(Desktop(), "Invoice Entry", policy=Policy.strict(allow=[...]))  # the walk only
walk.complete, walk.stopped, walk.findings
```

`audit(..., tab_walk=True)` runs the static rules first, then the walk, and
appends the `tab-*` findings to the same report. `tab_walk()` takes
`max_tabs`, `reverse_check`, `policy`, `confirm`, `settle` (seconds to wait
after each press before reading the focus, default 0.05), `selectors` and
`rules`. Pass a `GuardedDesktop` as the desktop to use its policy, audit log
and confirmation callback.

In the JSON report the walk appears as a `tab_walk` object next to
`findings`:

```json
"tab_walk": {
  "window": "Invoice Entry", "presses": 6, "reverse_presses": 5,
  "complete": true, "stopped": "cycle", "reverse_ok": true, "restored_focus": true,
  "stops": [{"index": 1, "role": "edit", "name": "Customer", "element": "...",
             "selector": "...", "bounds": {...}, "visible": true}]
}
```

`stopped` is `cycle`, `max_tabs`, `trap`, `escape`, `focus-lost`,
`interrupted`, `refused` or `dry-run`.
